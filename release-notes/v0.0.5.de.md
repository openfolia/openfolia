OpenFolia fügt sich jetzt in die eigene Anmeldung einer Organisation ein: Man meldet sich neben
OpenID Connect auch mit SAML 2.0 an, ein Verzeichnis legt die Personen per SCIM 2.0 an, und Admins
können Single Sign-on vorschreiben. Wer sich hier anmeldet, kann einen zweiten Faktor hinzufügen,
Benachrichtigungen kommen per E-Mail, und das Portal zeigt neben der neuesten Version auch ältere.

- Anmeldung: SAML 2.0 neben OpenID Connect, mit denselben Benutzern, Sitzungen, Zuordnungen von
  Gruppen zu Rollen und demselben Audit. Die Metadaten des Identity Providers kommen von einer
  https-Adresse oder aus einer Datei (CCMS_SAML_IDP_METADATA_URL oder CCMS_SAML_IDP_METADATA_FILE),
  und der Server stellt seine eigenen für den Provider bereit. Jede Antwort muss das eine
  Name-ID-Format der Installation tragen (CCMS_SAML_NAME_ID_FORMAT, Standard persistent). Eine
  Anmeldung, die beim Provider beginnt, ist aus, solange CCMS_SAML_IDP_INITIATED nicht true ist.
  Single Logout und verschlüsselte Assertions werden nicht unterstützt. Zur Anleitung:
  https://docs.openfolia.com/de/guide/self-hosting/saml
- SCIM: Ein Verzeichnis legt per SCIM 2.0 unter /api/scim/v2 Benutzer an, ändert und deaktiviert sie
  und pflegt Gruppen mit ihren Mitgliedern, mit dem Token eines Service-Accounts, dessen Rolle die
  neue Berechtigung scim.provision hat. Eine Deaktivierung wirkt sofort: Sitzungen enden und Sperren
  werden freigegeben, die Überarbeitungen der Person bleiben; Benutzer werden nie gelöscht. Eine
  angelegte Gruppe wird wie eine Gruppe des Identity Providers Rollen zugeordnet, gibt aber nie eine
  Rolle mit einer globalen Berechtigung. Jede Änderung steht im Audit-Protokoll.
- Single Sign-on vorgeschrieben: Unter Verwaltung › Projekteinstellungen › Installation › Single
  Sign-on und Sitzungen können Admins die Anmeldung über den Identity Provider vorschreiben.
  Passwörter, Codes per E-Mail, Einladungen und Links zum Zurücksetzen werden dann abgelehnt, bis
  auf das Passwort eines Notfallkontos; jede seiner Anmeldungen wird festgehalten und allen Admins
  als Benachrichtigung und E-Mail gemeldet. Beim Einschalten enden die Sitzungen, die nicht mehr
  erlaubt sind, und es wird abgelehnt, solange es die Person aussperren würde, die es einschaltet,
  oder solange ein SAML-Provider, dessen Metadaten von einer Adresse kommen, keine gültigen
  Metadaten liefert. Auf derselben Seite steht, wie lange eine Sitzung ungenutzt bleiben und wie
  lange sie höchstens dauern darf; ein offen gelassener Tab hält eine Sitzung nicht mehr am Leben.
  Endet eine Sitzung, sagt der Editor warum und gibt den ungespeicherten Text eines Moduls nach der
  erneuten Anmeldung zurück.
- Zwei-Faktor-Anmeldung: Wer sich mit Passwort oder einem Code per E-Mail anmeldet, kann im
  Kontomenü eine Authenticator-App mit Wiederherstellungscodes hinzufügen. Admins können sie für
  Admins oder für alle vorschreiben (Verwaltung › Projekteinstellungen › Installation ›
  Zwei-Faktor-Anmeldung) und den zweiten Faktor einer Person unter Verwaltung › Benutzer
  zurücksetzen; den des letzten Admins setzt ein Befehl auf dem Server zurück. Bei einem Identity
  Provider ist der zweite Faktor Sache des Providers.
- Benachrichtigungen per E-Mail: Unter Kontomenü › Benachrichtigungen legt jede Person für jede Art
  von Benachrichtigung fest: aus, nur in der App, sofort per E-Mail oder als tägliche
  Zusammenfassung zu ihrer eigenen Stunde und in ihrer Zeitzone; außerdem kann sie alle E-Mails
  pausieren. Die E-Mails kommen auf Deutsch oder Englisch mit Abmeldung per Klick; E-Mails, die eine
  Person über ein stündliches Limit hinaus bekäme, warten auf die Zusammenfassung
  (CCMS_NOTIFICATIONS_DIGEST_HOUR, Standard 8; CCMS_NOTIFICATIONS_EMAILS_PER_HOUR, Standard 20).
  Verwaltung › System › Mail zeigt die E-Mails, die endgültig nicht zugestellt wurden. Ohne
  Mailserver wird keine E-Mail eingereiht, und die Seite sagt warum.
- Personen: Die Arbeit einer deaktivierten Person trägt weiter ihren Namen, mit dem Zusatz
  „(deaktiviert)“, im Verlauf, in Prüfung und Kommentaren, bei Veröffentlichungen,
  Übersetzungsaufträgen, im Audit-Protokoll und in den Benachrichtigungen, bis sie wieder aktiviert
  wird.
- Portal: ältere Versionen. Mit CCMS_PORTAL_RELEASES_PER_PRODUCT (1 bis 20; der Standard 1 baut die
  Seite wie bisher) baut das Portal die neuesten Versionen jedes Produkts, und CCMS_PORTAL_RELEASES
  darf jetzt mehrere Versionen eines Produkts nennen. Eine ältere Version hat eigene Adressen und
  eine eigene Suche, beginnt mit einem Hinweis, der auf die neueste verlinkt, und bleibt
  Suchmaschinen verborgen, solange CCMS_PORTAL_OLDER_NOINDEX nicht off ist. Ein Versionswechsler im
  Kolophon der Anleitung wechselt die Version und behält die Anleitung, die Variante, den gerade
  gelesenen Abschnitt und den Bereich eines Update-Leitfadens. Jede Version hat eine eigene Seite
  mit Datum, Versionshinweisen und Anleitungen.
- Portal: eine Startseite, in OpenFolia geschrieben. Eine Anleitung, die CCMS_PORTAL_START nennt,
  gibt der Startseite Überschrift, Einleitung, einen Hinweis und hervorgehobene Links als Karten, zu
  Abschnitten, Anleitungen, Update-Leitfäden, Suchen, älteren Versionen oder anderen Adressen; sie
  wird geprüft und veröffentlicht wie jede Anleitung. CCMS_PORTAL_URL ist die eigene Adresse des
  Portals, sodass auch ein aus dem Portal kopierter Link geprüft wird, und ein Link, den die
  Zielgruppe nicht lesen darf, entfällt. Ohne CCMS_PORTAL_START bleibt die Startseite wie bisher.
- MCP: Das gemeinsame CCMS_MCP_HTTP_TOKEN entfällt, wie in v0.0.4 angekündigt. Jeder HTTP-Client
  sendet sein eigenes Token eines Service-Accounts; solange die alte Einstellung noch gesetzt ist,
  startet der MCP-Server nicht und sagt warum.
- Prüfung: Ist die Freigabe einer freigegebenen Überarbeitung verfallen (die freigebende Person hat
  die Rolle verloren oder wurde deaktiviert), sperrt die Prüfung das Zusammenführen, sagt warum und
  zeigt, auf welche Freigabe sie wartet.
- Überarbeitungen: Eine Vorschau, ein PDF oder eine Anleitung, die genau dann geöffnet wird, wenn
  die Änderungen einer Überarbeitung festgeschrieben werden, zeigt nicht mehr „nicht gefunden“ oder
  den Text von vorher. Eine Übersetzung als aktuell zu markieren überschreibt keinen Speicherpunkt
  mehr, der inzwischen festgeschrieben wurde; es wird stattdessen abgelehnt.
- Doku: Die Suche der Doku-Seite lädt nur die Sprache des Lesers, etwa ein Drittel des bisherigen
  Downloads, sobald sie geöffnet wird, und zeigt einen Ladezustand und bei einem Fehler „Erneut
  versuchen“.
- Demo: Der Leitfaden zum Software-Update ist ein Leitfaden für Besitzer, sodass ihn das gemeinsame
  Demo-Portal zeigt; seine zwei Schritte für Techniker stehen jetzt im Serviceheft.
- Sicherheit: Die Anmeldung über einen Identity Provider hält jetzt eine deaktivierte Person
  draußen, deren Konto beim Provider sich geändert hat, anhand einer Adresse, für die der Provider
  bürgt. SAML-Antworten werden getrennt vom übrigen Server und mit einem Zeitlimit geprüft, sodass
  keine Antwort den Server aufhalten kann. Wie die Verknüpfung über die Adresse funktioniert:
  https://docs.openfolia.com/de/guide/self-hosting/saml

Nicht abwärtskompatibel: CCMS_MCP_HTTP_TOKEN entfällt (in v0.0.4 angekündigt). Geben Sie vor dem
Upgrade jedem MCP-Client ein eigenes Token eines Service-Accounts (Verwaltung › Service-Accounts)
und entfernen Sie CCMS_MCP_HTTP_TOKEN und CCMS_MCP_HTTP_TOKEN_FILE aus den Einstellungen. Für das
Upgrade von v0.0.4 legen Sie zuerst ein Backup an und folgen deploy/README.md#upgrades; die
Datenbankmigrationen laufen beim Start. Frühere Versionen konnten bei der Anmeldung einen neuen
Benutzer für eine deaktivierte Person anlegen, deren Konto beim Provider sich geändert hatte, und
diese Benutzer bleiben aktiv: Prüfen Sie die Benutzer, die nach einer Deaktivierung durch eine
Anmeldung entstanden sind, und deaktivieren Sie sie bei Bedarf.
