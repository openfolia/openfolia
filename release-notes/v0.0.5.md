OpenFolia now fits into an organisation's own sign-in: people sign in with SAML 2.0 as well as
OpenID Connect, a directory provisions them with SCIM 2.0, and an administrator can require single
sign-on. People who sign in here can add a second factor, notifications come by email, and the
portal serves older releases beside the newest.

- Sign-in: SAML 2.0 beside OpenID Connect, with the same users, sessions, group-to-role mappings and
  audit. The identity provider's metadata is read from an https address or a file
  (CCMS_SAML_IDP_METADATA_URL or CCMS_SAML_IDP_METADATA_FILE), and this server serves its own for
  the provider. Every answer must carry the installation's one name ID format
  (CCMS_SAML_NAME_ID_FORMAT, default persistent). Sign-in begun at the provider is off unless
  CCMS_SAML_IDP_INITIATED is true. Single logout and encrypted assertions are not supported. The
  guide: https://docs.openfolia.com/guide/self-hosting/saml
- SCIM: a directory creates, updates and deactivates users, and keeps groups and their members, over
  SCIM 2.0 at /api/scim/v2, with the token of a service account whose role holds the new
  scim.provision permission. A deactivation takes effect at once: sessions end and locks are
  released, while the person's revisions stay; users are never deleted. A provisioned group maps to
  roles like an identity provider's group, but never gives a role with a global permission. Every
  change is in the audit log.
- Single sign-on required: under Admin › Project settings › Installation › Single sign-on and
  sessions, an administrator can require sign-in through the identity provider. Passwords, codes by
  email, invites and reset links are then refused, except the password of one emergency account;
  each of its uses is recorded and sent to every administrator as a notification and an email.
  Turning it on ends the sessions that are no longer allowed, and it is refused while it would lock
  out the person making the change, or while a SAML provider whose metadata comes from an address
  does not answer with valid metadata. The same page sets how long a session may stay idle and how
  long it may last; a tab left open no longer keeps a session alive. When a session ends, the editor
  says why and gives back a module's unsaved text after signing in again.
- Two-factor sign-in: people who sign in with a password or a code by email can add an authenticator
  app, with recovery codes, from the account menu. An administrator can require it for
  administrators or for everyone (Admin › Project settings › Installation › Two-factor sign-in) and
  reset a person's second factor in Admin › Users; a command on the server resets the last
  administrator's. With an identity provider, the second factor is the provider's.
- Notifications by email: under Account menu › Notifications each person chooses, for each kind of
  notification, off, in the app only, email at once or a daily summary at their own hour and time
  zone, and can pause all email. Emails come in English or German with a one-click unsubscribe, and
  emails at once beyond an hourly cap per person wait for the summary
  (CCMS_NOTIFICATIONS_DIGEST_HOUR, default 8; CCMS_NOTIFICATIONS_EMAILS_PER_HOUR, default 20). Admin
  › System › Mail lists the emails that failed for good. Without a mail server, no email is queued
  and the page says why.
- People: a deactivated person's work keeps their name, marked "(deactivated)", in history, review
  and comments, releases, translation jobs, the audit log and the notifications, until they are
  reactivated.
- Portal: older releases. With CCMS_PORTAL_RELEASES_PER_PRODUCT (1 to 20; the default 1 builds the
  site as before) the portal builds each product's newest releases, and CCMS_PORTAL_RELEASES may now
  name several releases of one product. An older release has addresses of its own and a search of
  its own, starts with a notice that links to the latest, and is kept out of search engines unless
  CCMS_PORTAL_OLDER_NOINDEX is off. A release switch in the manual's colophon changes the release
  and keeps the manual, the variant, the section being read and an update guide's range. Each
  release has a page with its date, its notes and its manuals.
- Portal: a start page written in OpenFolia. A manual named by CCMS_PORTAL_START gives the start
  page its heading, introduction, a notice and featured links as cards, to sections, manuals, update
  guides, searches, older releases or other addresses; it is reviewed and released like any manual.
  CCMS_PORTAL_URL is the portal's own address, so a link copied from the portal is checked too, and
  a link the audience may not read is left out. Without CCMS_PORTAL_START the start page is as
  before.
- MCP: the shared CCMS_MCP_HTTP_TOKEN is removed, as announced in v0.0.4. Every HTTP caller sends
  its own service account token; while the old setting is still set, the MCP server refuses to start
  and says why.
- Review: while an approved revision's approval has lapsed (its approver lost the role or was
  deactivated), the review panel blocks Merge and says why, and marks the approval it waits for.
- Revisions: a preview, a PDF or a manual opened at the moment a revision's changes are committed no
  longer shows "not found" or the text from before. Marking a translation as current no longer
  overwrites a save point committed meanwhile; it is refused instead.
- Docs: the docs site's search loads only the reader's language when it opens, about a third of the
  download before, and shows a loading state, and an error with "Try again".
- Demo: the software update guide is an owner guide, so the shared demo portal shows it; its two
  technician steps moved to the service booklet.
- Security: sign-in through an identity provider now keeps out a deactivated person whose account at
  the provider changed, by an address the provider vouches for. SAML answers are checked apart from
  the rest of the server and within a time limit, so no answer can hold the server up. How linking
  by address works: https://docs.openfolia.com/guide/self-hosting/saml

Breaking: CCMS_MCP_HTTP_TOKEN is removed (v0.0.4 announced it). Before upgrading, give every MCP
caller its own service account token (Admin › Service accounts) and remove CCMS_MCP_HTTP_TOKEN and
CCMS_MCP_HTTP_TOKEN_FILE from the settings. To upgrade from v0.0.4, take a backup first and follow
deploy/README.md#upgrades; the database migrations run at start-up. Earlier versions could make a
new user at sign-in for a deactivated person whose account at the provider had changed, and those
users stay active: review the users created by sign-in after a deactivation, and deactivate them if
needed.
