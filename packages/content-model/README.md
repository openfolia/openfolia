# @openfolia/content-model

The document model at the core of the platform. Every other part (editor, API, PDF and HTML renderers, translation export, RAG chunks, importers) reads and writes this tree. AsciiDoc in Git is only its storage format.

## Shape

```
Module
├─ schemaVersion        bumped on breaking changes; each bump ships a migration
├─ id                   slug, doubles as the file name
├─ meta                 title, type, lang, audience, facets, keywords, source, deprecated
└─ blocks: Block[]
```

**Blocks.** Every block has a stable `id`, written to AsciiDoc as `[#id]`. Translations, comments, RAG chunks and import traceability all key on it.

| Block         | Holds                                                  | Notes                                                  |
| ------------- | ------------------------------------------------------ | ------------------------------------------------------ |
| `paragraph`   | inline content                                         |                                                        |
| `section`     | title + blocks                                         |                                                        |
| `list`        | items (inline + blocks)                                | `ordered: true/false`                                  |
| `procedure`   | optional title + steps (inline + blocks)               | task steps, rendered and chunked separately from lists |
| `table`       | columns, header flag, rows of cells (blocks)           | cells support colspan and rowspan; a cell may be empty |
| `image`       | content-hash asset, alt text, optional title and width | alt text is required; optional callouts                |
| `attachment`  | content-hash asset, name, optional description, file   | a file readers download; see "Attachments"             |
| `safety`      | severity, hazard (inline), symbols, blocks             | danger, warning, caution, notice                       |
| `admonition`  | blocks                                                 | note, tip, important; never for safety                 |
| `faq`         | question (inline) + blocks (the answer)                | one FAQ entry; see "FAQ entries"                       |
| `variant`     | condition + blocks                                     | the only way to vary content by variant                |
| `moduleRef`   | module id, optional block id                           | reuse; resolved at build time; see "One block"         |
| `literal`     | preformatted text                                      | not translated                                         |
| `passthrough` | raw source text                                        | importer escape hatch, flagged by validation           |
| `pageBreak`   | nothing                                                | a new page in the PDF; see "Page breaks"               |

**Attachments.** An `attachment` block is a file of any kind readers download from the module (a ZIP of configuration files, a JSON sample, a datasheet). Like an image it refers to its file by content hash (`asset`, `sha256:<hash>`), so a release tag pins the exact bytes. `name` (required, 1 to 200 characters) is the link text and `description` (optional, at most 1,000) says what the file is for; both are translated per language like an image's alt text, one line each. `fileName` (the name a download is saved under), `mediaType` and `size` (bytes) describe the stored file and are filled in from it when the file is attached; they are the same in every language. `FileName` is one name, never a path: 1 to 255 characters, none of `< > : " / \ | ? *`, no control characters or invisible direction marks, no leading or trailing whitespace, no trailing dot, in NFC; `toFileName(raw)` turns an uploaded file's name into one (its last path segment, forbidden characters as `_`, cut to 255 keeping the extension). `MediaType` is a lowercase `type/subtype` without parameters, as the blob store keeps it.

**FAQ entries.** An `faq` block is one frequently asked question: `question`, one line of inline content (like a safety block's hazard), and `blocks`, its answer (at least one block: paragraphs, lists, images, notices; no sections or page breaks, as in any delimited block). The question is a translation unit of its own (field `question`), and the answer's blocks are units as anywhere. In AsciiDoc it is `[faq#id]`, the question as a `.Title` line, the answer between `====` delimiters. A Q&A list (`[qanda]`, entries `Question::`) is read too, one FAQ entry per question: each entry takes its ID from a `[[id]]` anchor before the question (the first may take the list's `[qanda#id]` instead), its answer is a paragraph after `:: ` or on the next line, starting with its own `[[id]]` anchor, then any blocks attached with `+`. It is always written back as `[faq#id]` blocks. The HTML renders it as a disclosure (`<details>`), the PDF as the question in bold over its answer, and `toChunks` gives each entry a retrieval chunk of its own (see "Retrieval chunks").

**Image callouts** (`callouts.ts`, #498). An image block may carry `callouts`: numbered markers on this use of the picture (not on the asset, so the same picture carries other callouts in another module), at most `MAX_CALLOUTS` (100), never an empty list. Each `Callout` has an `id` (a block ID, unique among the module's block IDs, so a reference, a translation or a comment names it like a block; the `Module` schema refuses a clash), an `anchor` (the point it marks) and an optional `label` (where its number is drawn, with a leader line to the anchor), each `{ x, y }` from 0 to 1 across and down the image, so they survive the picture being replaced at another resolution; its `legend` (one line of inline content with marks, translated with the module), an optional `when` (a condition, as on a variant block: the callout shows only where it holds) and an optional `style` (one of the configured `calloutStyles`; none is the default marker, a filled circle with its number). **Numbers are derived, never stored**: `numberCallouts(image, visible?)` counts 1, 2, 3 over the callouts a variant shows, so there are no gaps, in the image's `calloutOrder`: `reading` (the default: rows of `CALLOUT_ROW_BAND`, 5 % of the height, top to bottom, left to right in a row, by `markerPoint`, the label if there is one; ties in the stored order) or `manual` (the stored order, the author's). An image's `calloutLegend` (`CALLOUT_LEGENDS`) says where the outputs print its legend: `below` (the default, left out by `normalizeModule`), `beside` (at the end of the line, so the left in right-to-left text) or `none` (the markers only). `calloutNumbers(image, holds?)` gives them by callout ID. Coordinates keep `COORDINATE_DECIMALS` (4) places: `normalizeModule` rounds them (`roundCoordinate`) and drops `calloutOrder: 'reading'`. An inline `calloutRef` (`{ type: 'calloutRef', block, callout }`) refers to a callout of an image block in the same module and reads as its number in the manual (`calloutNumber(manual, ref)`); `calloutRefs(blocks)` lists them, `imagesById(blocks)` the images. `validateModule` reports a reference to an image or callout the module does not have (`unknown-callout`), an unconfigured style (`unknown-callout-style`) and a callout's condition as a variant block's. Whether a reference's callout shows is the variant's question: `resolveManual` reports it (below). Each callout's legend is a translation unit of its own (#548, "Translation"). `hasLegendBeside(manual)` says whether a resolved manual prints a legend beside an image, which its PDF's layout then checks for room (`callout-label-overflow`).

**Table caps** (#686, `table-limits.ts`). A table has at most `MAX_TABLE_COLUMNS` (1,000) columns and covers at most `MAX_TABLE_CELLS` (50,000) cells, its rows times its columns: the area its grid lays out, a cell spanning several counted once per place, so few cells spanning a large area count as large. The tables of one module (one language file) cover at most `MAX_MODULE_TABLE_CELLS` (1,000,000) places together (`tablesTooLarge`; the parser stops at the table that passes it, the `Module` schema refuses it with `params.code` `table-too-large` at `blocks` and checks no table's grid), and a manual or a chunk at most `MAX_EXPANDED_TABLE_CELLS` (the same) over every inclusion of its modules ("The expanded size"), so thousands of tables at the cap never add up. Far above real content (the largest table in the fixtures and sample content is 2 columns by 3 rows; the scale generator's at most 5 by 17), and the importer's DITA tables already had the same caps. Not a setting, so whether content is valid never depends on the deployment. `tableTooLarge(columns, rows)` says why a table is past them (or `undefined`); `assertTableWithinLimits(table)` throws `TableTooLargeError` (`code` `table-too-large`, `tableId`). Each place that lays out a grid refuses a table past the caps before it lays out a row: the AsciiDoc parser (`AsciidocParseError` with `code` `table-too-large`, before a row past the cap is made), the `Table` schema (a custom issue, `params.code` `table-too-large`; `checkStructure` reads none of its rows), the import validator (`table-too-large`), the chunker, the HTML and Typst renderers and the DITA export. Counted in the tests (rows, cells or columns read), never timed.

**Page breaks.** Spacing and page layout are the design's job: empty paragraphs are not content. A `pageBreak` block is the one layout choice an author makes: the PDF starts a new page after it (a weak break, so never an empty page), and the HTML shows it only in the editor's preview, as a marker. It goes only where a page can break, at module level or directly in a section, never in a list, a table, a notice or a variant block (`checkStructure`, so the `Module` schema refuses it). In AsciiDoc it is `<<<` under its `[#id]` line, and takes no `.Title`.

**Inline content** mirrors ProseMirror: text runs with marks (`strong`, `emphasis`, `code`, `sub`, `sup`, `ui`, `link`, `term`), plus `attribute` (a named value filled in per manual and variant), `xref`, `kbd`, `calloutRef` (a callout's number, above), `hardBreak` and `placeholder` (`placeholder:<key>[]` in AsciiDoc: a value a page design's text takes from the manual, such as its title or the page number, "Page designs"; only a design holds one, a module with one is the validation error `placeholder-in-module`). A link's `href` is `LinkHref`: an absolute `http:`, `https:` or `mailto:` URL with a host (or an address), no whitespace and none of `[`, `]` or `|`; `isLinkHref(x)` is the same check for the editor and the renderers, so no other address is stored or rendered.

**Term links** (#245). A `term` mark (`{ type: 'term', termId }`, a `TermId`) says the text it marks is the term of that ID: the outputs link it to its definition and list it in the manual's glossary. In AsciiDoc it is a span with the roles `term` and the ID, `[.term.charger]##charger##`; other marks go inside it, and a UI label holds it as `[.term.save]##[.ui]##Save####`. A text run carries at most one of `link` and `term` (a term link is a link), and neither is allowed in cross-reference text or in a term's definition (shown where a term link is). `termLinks(blocks)` (`term-links.ts`) lists every link with the block (or list item) it is in, neighbouring runs of one link (split by other marks) once; `linkedTermIds(blocks)` the terms, each once; `ownInlineContent(node)` is a block's own inline content, which both walk. Whether a linked term exists is the API's check (`unknown-term`, `deprecated-term`), never a parse error.

**Conditions** are a small expression tree: `all`, `any`, `not`, `in` (enum attributes) and `cmp` (version attributes, compared numerically). `conditionIssues(condition, config)` checks one against the configuration: every attribute it names is configured (`unknown-variant-attribute`), every `in` value is one of an enum attribute's values (`unknown-variant-value`) or, for a version attribute, a dotted version (`invalid-version-value`), a `cmp` compares a version attribute (`version-compare-on-enum`), and the version a `cmp` compares with is a dotted version (`Version`, the form `compareVersions` reads; `invalid-version-value`). The `Condition` schema refuses such a version already, so a module or manifest file with one does not parse; a condition from `parseCondition`, which reads any word, reaches `conditionIssues` with it (`software >= abc`).

**Keywords.** `meta.keywords` is an optional list of free-form keywords in the module's language (each language file has its own), for finding a module: unlike facets they are not configured. `Keyword` trims a keyword, writes runs of whitespace as one space and stores it in NFC; it has 1 to 64 characters (`MAX_KEYWORD_LENGTH`) and no comma or control character. Repeats, case aside (`keywordKey`), are dropped with the first spelling kept, and a module has at most 32 (`MAX_KEYWORDS`). An empty list is the same as none (`normalizeModule` drops it). In AsciiDoc: `:keywords: battery, maintenance`.

**Deprecation** (`deprecation.ts`, #266): a module or manual withdrawn or superseded has `deprecated` (`Deprecation`): `reason`, one line of plain text in NFC, 1 to `MAX_DEPRECATION_REASON_LENGTH` (500) characters, and an optional `replacedBy`, the module (for a module) or manual (for a manual) to use instead. It is metadata like the title: made and undone through a change set, never removed automatically. A module's deprecation is its source-language file's (`meta.deprecated`; a translation's own is not read). In AsciiDoc: `:deprecated: <reason>` and `:replaced-by: <id>` (only with `:deprecated:`); in a manifest, `deprecated: { reason, replacedBy }` after `audience`. Deprecated content stays valid, readable and in manuals: `validateModule` and `validateManifest` only warn when `replacedBy` names the module or manual itself (`unknown-replacement`); whether a replacement exists is the repository's question (the API's checks report it with the same code), and a manual including a deprecated module is the API's `deprecated-module` warning.

**Config.** Everything organisation-specific is configuration (`ProjectConfig`): languages, module types (and which need special approval, which hold snippets, and which are safety content, `safety: true`, what a derived manual gathers by default, #451), ordered audience levels, facets, variant attributes, text attributes, safety symbols, callout styles (`calloutStyles`, optional, each `{ id, label }`) and `outputLabels`, the fixed texts an output prints per manual language (signal words, "Contents", figure and table captions, the attachment label and the PDF's note that an attached file is downloaded from the online version; any subset per language tag, over the shipped `DEFAULT_OUTPUT_LABELS` for English, German, French, Arabic and Hebrew; `resolveOutputLabels(lang, config.outputLabels)` gives the set with English for a missing key, which `resolveManual` reports as a `missing-label` warning), and `maxHeadingLevel`, the deepest heading level the editor offers (Heading 1 is a section at the top of a module, Heading 2 a section in it; 1 to `MAX_SECTION_DEPTH`, default `DEFAULT_MAX_HEADING_LEVEL`, 3). The cap is the editor's: a module stored with deeper sections, up to the model's own `MAX_SECTION_DEPTH` of 5, stays valid. A variant attribute's value may be `archived: true`: content using it stays valid, but editors no longer offer it, so archiving is how a value in use is retired. The file is `openfolia.yaml` at the repository's root (`CONFIG_FILE_NAME`, in `/core` too); for one release a repository that has only the earlier name, `ccms.yaml` (`LEGACY_CONFIG_FILE_NAME`), is still read, with a deprecation warning, and `openfolia.yaml` wins when both exist (`isConfigFileName` is true for either). `parseConfig` and `printConfig` read and write `openfolia.yaml` (canonical YAML: the schema's key order, defaults left out; `printConfig(parseConfig(t)) === t` for every `t` it prints; comments are not kept); `StrictProjectConfig` is `ProjectConfig` refusing unknown members at every level, for a configuration someone sends to be stored. `codeLanguages` (optional, default none) adds languages to the editor's code block picker beside the ones it ships: each `{ id, label }`, the id one word as the block stores it (`"fortran"`, `"c++"`), the label its display name. `release.productFacet` (optional) names the facet whose values are the products a release is cut for; `productFacet(config)` gives it, or the first facet without it (undefined when there are no facets). `release.checkManufacturer` (optional, default off, #395) makes every manual's checks warn (`missing-manufacturer`) while there is no `manufacturer`. `manufacturer` (optional, #395, `Manufacturer`) is who makes the product: `name` (one line, at most `MAX_MANUFACTURER_LINE`, 200 characters), `address` (up to `MAX_MANUFACTURER_ADDRESS_LINES`, 10, lines), `contact` (one line) and `website` (a `LinkHref`: `https:`, `http:` or `mailto:`); a page design's back page prints it, and the placeholders `manufacturer-name`, `manufacturer-address`, `manufacturer-contact` and `manufacturer-website` show it on any page. `styleGuide` (optional, 1 to `MAX_STYLE_GUIDE_LENGTH`, 20,000 characters, trimmed) is the house style in plain words, which the API's model-based style review sends with a module's text when an author asks for one. `pdf.standard` (optional, `PDF_STANDARDS`) is the standard every manual's PDF is made to: `ua-1`, PDF/UA-1, tagged and accessible (the default, `DEFAULT_PDF_STANDARD`; a document that cannot meet it is refused, `@openfolia/render-typst`'s README, "Accessibility"), or `none`, a plain PDF; `printConfig` leaves the default out. `pdf.design` (optional) names the page design of every manual whose manifest names none ("Page designs"). `pdf.calloutLabelMinSize` (optional, #548, points from `MIN_CALLOUT_LABEL_SIZE` to `MAX_CALLOUT_LABEL_SIZE`, 4 to 12; absent: `DEFAULT_CALLOUT_LABEL_MIN_SIZE`, 6, which `printConfig` leaves out) is the smallest text a callout legend beside its image shrinks to in the PDF before what still does not fit is cut off and reported. `delivery` (optional, #450, `delivery.ts`) sets the stable addresses: `access` (`DELIVERY_ACCESS`: `public`, `signed-in`, the default, or `off`), `publicAudience` (the audience level a public reader reads up to, default the first; it must name an audience), `missingLanguage` (`picker`, the default, or `source`), `pdfQrCode` (`none`, the default, `title-page` or `back-cover`; printed only when `access` is `public`) and `manuals`, by manual ID, `{ slug?, formerly }`: the manual's address segment (default its ID) and up to `MAX_FORMER_ADDRESSES` former ones that redirect to it; no two manuals may share an address, current or former. `deliverySlug`, `manualOfSlug`, `manualIdsOf` and `publicAudience` read it. **Labels per language** (#731, `localized-text.ts`, `config-units.ts`, `config-translation.ts`). Every configured `label` (module types, audiences, facets and their values, variant attributes and their values, text attributes, safety symbols, callout styles) is a `LocalizedText`: one text for every language (`label: Task`, printed back as written), or one per language by language tag (`label: { en: Task, de: Handlung }`, printed with its languages sorted); a language without its own shows the source language's. `StrictProjectConfig` refuses a label written per language without the source language's (`ProjectConfig`, reading a file, takes it, falling back to its first version). `textIn(text, lang, source)` gives the text to show (its own, else the source language's, else its first), `ownTextIn` and `sourceTextOf` its own version, `withTextIn(text, lang, source, value)` sets or removes one language's (a map left with the source language alone becomes one text again), `printableText` the printed form; `localizedText(single)` is the schema. For readers: `labelsIn(config, lang)` gives the configuration with every label a string in `lang` (`ConfigLabelsIn<C>`, any object shaped like the configuration, the API's JSON too), `labelOf(config, list, id, lang)` one label, `variantLabel(variant, config, lang)` a variant as people name it (`Large · Software 2.3`). `translations` (optional, printed after `calloutStyles`) records per target language what its labels were translated from, as a manifest's record (`ConfigTranslationRecord`, `{ sourceCommit, blocks }`, keyed `ConfigUnitKey`: `moduleTypes.<id>`, `audiences.<id>`, `facets.<id>`, `facets.<id>.<value>`, `variantAttributes.<id>`, `variantAttributes.<id>.<value>`, `textAttributes.<id>`, `safetySymbols.<id>`, `calloutStyles.<id>`). `configUnits(config, source)` (in `/core` too) lists the labels as units (a section's `title` part, plain text; `configTexts` the texts by key, a list's items in order, an item's values right after it); `compareConfigWithRecord`, `hasConfigTranslation`, `mergeConfigTranslation`, `markConfigCurrent` and `configSourceHashes` are the translation status's, import's and mark-current's, sharing `text-record.ts` with the manifest's. A label of one text for every language is `missing` in a target language, as a cover image's alternative text is: a name that stays the same (a product name) is given per language. Every key of the schema carries a description (`.describe()`: what it decides, its format, its effect when left out), which the docs site's `openfolia.yaml` reference shows and the generated OpenAPI carries; a key without one fails `config.spec.ts` and the docs build. Nothing in this package names a company, product or market.

**Snippets** (`snippet.ts`): reusable wording (a standard sentence, a safety paragraph) is a module of a type marked `snippet: true` in `moduleTypes`, so storage, versions, review, translation and where-used are a module's. Which types are snippets is configuration: `snippetTypes(config)` lists them, `isSnippetType(config, type)` asks. A snippet is one or a few blocks of text: `validateModule` warns at a section or a module reference in one (`snippet-too-large`, `blocksTooLargeForSnippet`). It is inserted by reference (a `moduleRef`, kept in sync) or copied (its blocks with new IDs). `plainTextExcerpt(blocks, max = 200)` is the start of a module's plain text, in document order and white space collapsed, a text attribute as `{name}` (its value depends on the manual), cut by characters; `foldText(text)` folds text for comparing as search does (case, diacritics, `ß` as `ss`, white space), so a snippet is matched alike in the API and the editor.

**Text direction** (`direction.ts`, #458). Every language is written left to right or right to left (`TextDirection`, `TEXT_DIRECTIONS`). `defaultDirection(tag)` takes it from the tag's script, as `Intl.Locale` fills it in (`ar`, `he`, `fa`, `ur`, `yi`, `dv`, … and any tag with an explicit right-to-left script such as `az-Arab`: `RTL_SCRIPTS`); `languages.direction` in `openfolia.yaml` (optional, `{ <tag>: ltr | rtl }`) overrides it per language, and `languageDirection(tag, config)` gives the one in force. `printConfig` writes it sorted and leaves out entries for languages that are not configured; `languageDirectionIssues(config)` lists those entries (`unknown-direction-language`, at `languages.direction.<tag>`, sorted by tag), never refused, only reported (`GET /config`, `meta.directionIssues`, #396). `resolveManual` stores the directions of the manual's language and of the source language (a module that fell back to it) in `ResolvedManual.directions`; `directionOf(manual, lang)` reads them (own entries only, `ltr` or `rtl`, else `ltr`), so the renderers need no configuration. A table column's `align` `left` and `right` are the start and end of the text: mirrored in right-to-left text. Nothing names a language's direction in code.

**Terms** (`term.ts`): the words everyone must use for a concept, and the ones they must not, per language. A `Term` is stored as `terms/<id>.yaml`, one concept per file, the ID being the file name (`TermId`: a module ID's form; `export` is reserved, `RESERVED_TERM_IDS`, since it names the export route next to the terms'): `schemaVersion`, a `status` (`proposed`, `approved`, `deprecated`), an optional `domain`, an optional `replacedBy` (the term to use instead; only on a deprecated term, never itself) and, per language (a tag in its canonical case, at least one), the `preferred` variant, `allowed` and `forbidden` variants (each `{ term, note? }`), an optional `definition` and an optional `usage` note. The definition is inline content (`TermDefinition`: text runs with the editor's marks and line breaks, no attributes, cross-references or keys, which depend on a manual; at most 10,000 characters) and is stored as AsciiDoc inline markup (`printDefinition`), so the file stays readable:

```yaml
schemaVersion: 1
status: approved
domain: charging
languages:
  en:
    preferred: charger
    allowed:
      - term: charging unit
    forbidden:
      - term: loader
        note: Reads as a machine that loads goods.
    definition: The device that charges the **battery**.
    usage: Name it in full on first use.
```

Strict: unknown members are refused. `parseTerm` / `printTerm` (canonical YAML, languages sorted, empty lists left out) round-trip, and an invalid file is a `TermParseError` naming the path in it (`languages.en.definition: …`). `validateTerm(term, config)` reports a language the configuration does not hold (`unknown-language`); whether `replacedBy` names a term is the repository's question, not one file's. `definitionText` is a definition as plain text, `termVariants` a language's variants (preferred, allowed, forbidden), and `termMatches(term, query, langs?)` whether the query, folded as search folds (`foldText`), is part of a variant or the definition.

**Term export** (`term-export.ts`): `termsToTbx(terms, { sourceLang, langs? })` writes TBX-Basic (ISO 30042:2019, DCA style): a `conceptEntry` per term (`id` `term-<id>`, `tbxConceptId`, since an XML ID cannot start with a digit), the domain as `subjectField`, a replacement as a `crossReference` (only when that term is in the file too), a `langSec` per language with the definition as plain text and the usage note as `note`, a `termSec` per variant with its `administrativeStatus` (preferred: `preferredTerm`, allowed: `admittedTerm`, forbidden: `deprecatedTerm`; a deprecated concept's preferred and allowed variants `supersededTerm`) and its note. The concept's status otherwise has no TBX-Basic data category. Everything is escaped (`escapeXml`; characters XML cannot hold become U+FFFD). `termsToCsv(terms, { langs? })`: a header row (`TERM_CSV_COLUMNS`), then one row per term and language, CRLF line endings, allowed and forbidden variants one per line in their cell, the definition as plain text; `csvCell` quotes as RFC 4180 does, and also a cell holding a semicolon or a tab (so it stays one cell where a spreadsheet splits on those), and puts a `'` in front of a value a spreadsheet would run as a formula: one whose first character other than whitespace is `=`, `+`, `-` or `@`, in ASCII, full width (`＝`, `＋`, `－`, `＠`) or small form (`﹦`, `﹢`, `﹣`, `﹫`), zero-width characters skipped like whitespace, or that starts with a tab or a carriage return. A negative number gets one too (`'-5`, read as text). With `langs`, only those languages, and a term holding none of them is left out.

**Module references** (`module-references.ts`): `namesModule(module, id)` says whether a module's blocks name module `id` (a `moduleRef` block or an `xref`, at any depth: sections, lists, tables, notices, variant blocks, titles and link texts), and `renameModuleReferences(module, from, to)` gives the module with each of them naming `to` (block IDs, a cross-reference's block and link text kept; the same object when none names `from`). `manifestNamesModule` and `renameManifestModule` do the same for a manifest's entries, groups included. `replacementNamesModule(module, id)` and `renameReplacement(module, from, to)` do it for a module's deprecation (`meta.deprecated.replacedBy`, #360; the same object when it is not `from`); a manual's `replacedBy` names a manual, not a module. The API's module rename uses them (`backend/api/README.md`, "Save points"). `crossReferencedModules(blocks)` lists the modules the blocks cross-reference, each once, in document order (#796).

## Writing checks

The terminology and style checks (#55, `writing-check.ts`, `style-pattern.ts`): pure, schema-free
and in `/core`, so the API's checks, the CLI check and the editor's writing aids (#247) run the
same code.

- **Input.** `compileWritingRules({ terms, styleRules, terminology, lang })` compiles once:
  `terms` are the `Term`s, `styleRules` and `terminology` the `openfolia.yaml` keys below, `lang` the
  module's language. `checkWriting(module, rulesOrInput)` checks a module's translatable text
  (the fields `translatableUnits` gives, never literal, code or passthrough blocks, code-marked
  text or atoms); `checkWritingText(content, rules)` checks one inline content (an editor's
  paragraph). Both return `{ findings, complete, stopped? }`.
- **A finding**: `code` (`forbidden-term` or `style-rule`), `severity` (`warning` or
  `blocking`), `blockId` (and `image` for a callout's text), `field`, `start` and `end` (UTF-16
  offsets in `plainTextOf(content).text`, as style-review suggestions use), the matched `text`,
  the `rule` (`{ kind: 'term', termId, status, note? }`, `{ kind: 'style', ruleId }` or
  `{ kind: 'sentence-length', words, max }`), an English `message`, and `replacement` when there
  is one.
- **Terms.** A forbidden variant of an approved term in `lang`, matched as whole words in any
  case, without stemming, white space runs matching any white space: the replacement is the
  term's preferred variant, in the case found (`adaptCase`). Severity: `warning`, `blocking` with
  `terminology.forbiddenIsBlocking`. Any variant of a deprecated term is a warning, its
  replacement's preferred variant suggested; a variant an approved term also uses is not. Proposed
  terms check nothing. Lookup is a trie of folded words, so its cost does not grow with the number
  of terms.
- **Style rules**, `styleRules.<lang>` in `openfolia.yaml`: `maxSentenceWords` (5–200) and up to 200
  `rules`, each an `id`, `words` (a phrase, as terms are matched) or `pattern`, `matchCase`
  (patterns), `message`, `replacement` and `severity` (`warning` by default). A language must be a
  configured one.
- **Patterns** (`StylePattern`) are untrusted configuration, so they are a subset of regular
  expressions matched by a Pike VM (Thompson NFA) in time linear in the text: literals, `.`,
  classes and `\d \w \s` (Unicode), `(…)` and `(?:…)`, `|`, `? * +`, `{n}`/`{n,m}` up to 20, `^`
  `$` `\b` `\B`. No back-references, lookaround, lazy quantifiers or nested counts; at most 200
  characters and 300 states; a pattern that matches the empty text is refused.
  `stylePatternProblem(source)` says why one is refused, and the config schema uses it.
  Matches are leftmost-longest and do not overlap.
- **Bounds.** At most 1,000,000 characters and 1,000 findings per check, and a budget of
  60,000,000 matcher steps across all patterns; past one, the check stops and says which
  (`stopped`: `chars`, `findings`, `steps`). A module of 1,000,000 characters against 10,000 terms
  and 200 rules checks in about 2 s on a loaded machine (`backend/api/tests/perf/`).

## Deliberately not in the model

- **Workflow status.** Derived from Git (latest release plus open change set), never stored.
- **Inline conditions.** Words that change per variant use `attribute` nodes. Block-level `variant` covers the rest. This keeps translation units whole.
- **AsciiDoc preprocessor features** (`ifdef`, `include::`). They are resolved before parsing, so they can't round-trip.

## Storage format (AsciiDoc)

`printModule(module)` writes canonical AsciiDoc; `parseModule(source, { id })` reads it back. `src/fixtures/battery-charging.adoc` shows the format. The module ID is the file name.

- Every block starts with an attribute line (`[#id]`, `[safety#id,severity=warning]`); list items and table cells carry `[[id]]` anchors. An empty table cell is a bare `|`.
- Our own block types use standard extension points: block styles (`safety`, `procedure`, `variant`), two block macros (`module::id[]`, or `module::id[block=<block-id>]` for one block of it, `attachment::sha256:<hash>["name",file=…,type=…,size=…,description=…]`) and AsciiDoc's own page break (`<<<`). An attachment is a block macro rather than an inline `link:`, since it is a block of its own with its facts; its name is always quoted (as an image's alt text), the named values are quoted when they are not plain words, and it takes no `.Title` line.
- Nested `====` blocks get one more `=` per level; verbatim blocks get a fence longer than any fence-like line inside.
- An image's callouts are an AsciiDoc callout list right below its `image::` line, one `<.>` item each (the auto-numbered form: the number is derived, so the file holds none, and `<1>` is refused): the callout's attribute list, then its legend: `<.> [callout#power-switch,x=0.25,y=0.4,label-x=0.1,label-y=0.05,style=square,when="model in (l-400)"] Power switch`. `x` and `y` are required, `label-x` and `label-y` go together, `style` and `when` are optional; coordinates are written with at most 4 places. `callout-order=manual` on the image macro is the author's order, `callout-legend=beside` (or `none`) the legend's place. A callout reference is the inline macro `callout:<image-block>#<callout>[]` (so `callout:` in text is escaped, `\callout:`).
- Inline marks always use the unconstrained forms (`**`, `__`, ` `` `, `[.ui]##…##`, `[.term.<id>]##…##`), and every markup character in text is backslash-escaped. Lines that could read as block syntax start with `{empty}`.
- The same module always prints to the same bytes. A property test generates random modules full of markup-like text and checks `parse(print(m))` equals the normalized `m`.

The parser is our own, not Asciidoctor.js: Asciidoctor turns inline markup straight into HTML, so it can't give us the inline tree, and our files only use the subset above.

**Known differences when the files are rendered by plain Asciidoctor** (for example a Git web preview; our own renderers are not affected): escaped characters such as `\_` may show their backslash, `~sub~`/`^sup^` text containing spaces is not rendered as sub/superscript, typographic replacements (`--`, `...`, `(C)`) apply, our block styles and `module::` render as plain blocks, and an image's callout list renders as a numbered list after it (with each callout's attribute list as text; Asciidoctor warns that no callout marks it) and a callout reference as text.

## Manuals and variants

A manual is a YAML manifest (`src/fixtures/operating-manual.yaml`): its title (`ManualTitle`, #731: one line for every language, or one per language as a configured label is, `textIn` the one to show; a group's title the same) and audience, the variant combinations actually shipped, values for text attributes (which may differ per variant), and the modules in order, optionally grouped and filtered with `when:`; `glossary: true` ends the manual with a glossary of the terms it links (#245); `coverImage` (#394, optional) is the cover image its page design's image slot shows: `default` (`{ asset, alt }`, the manual's) and `variants` (`{ variant, asset, alt }`, one variant's own, by its exact values, which wins), `alt` required, one text or one per language (`CoverImageAlt`); `validateManifest` reports one for a variant the manual does not build, or a second for the same variant (`unknown-cover-variant`, a warning) an alternative text in a language not configured (`unknown-language`), and one written per language without the source language's (`missing-cover-alt`, blocking); at most 500 characters each. `validateManifest` reports a title or group title written per language without the source language's (`missing-source-title`, an error) and one in a language not configured (`unknown-language`). `translations` (#656, optional, printed after `coverImage`, languages and keys sorted; not part of the import format) records what each target language's title, group titles (#731) and cover image text were translated from, as a page design's record does: `{ sourceCommit, blocks }`, `blocks` keyed `title`, `group.<12 hex>` (`groupUnitKey(title)`: the SHA-256 of the group's source-language title, so groups of the same title share one unit and moving a group keeps it) and `coverImage.default` or `coverImage.variant-<12 hex>` (`ManifestUnitKey`, `coverUnitKey(variant?)`: the SHA-256 of the variant's slug), at most `MAX_MANIFEST_UNITS`. `manifestUnits(manifest, source)` (in `/core` too) lists those texts as units: the title and each group's title once, in document order (a section's `title` part), then the cover images (an image's `alt` part; a variant's first entry only), each plain text (`manifestTexts` the texts by key); a merged group title goes into every group of that title; `compareManifestWithRecord`, `hasManifestTranslation`, `mergeManifestTranslation` and `markManifestCurrent` (and `markDesignCurrent` for a design) are what the API's translation status, import and mark-current use. `parseManifest` / `printManifest` read and write it; `validateManifest` checks it against the configuration.

**Derived manuals** (#451, `derive.ts`). A manifest with `kind: derived` (printed right after `schemaVersion`) has no entries of its own: its `rule` (`DerivedRule`, printed last, in place of `entries`) gathers them from another manual, such as a safety leaflet made of an operating manual's safety modules. `rule.source` names the source manual (an assembled one); `moduleTypes` the types gathered (absent: every type the configuration marks `safety: true`, `safetyTypes(config)`; `gatheredTypes(rule, config)`); `exclude` modules of the source left out on purpose; `front` and `back` the manual's own modules before and after (a title, a general introduction, contacts); each list at most `MAX_RULE_MODULES`, every module once. `deriveManifest({ manifest, source, config, moduleType })` gathers them: every module entry of the source (groups included, groups not kept) whose type is gathered and that the rule does not exclude or name as front or back matter, in the source's order, once (its first place), under the condition it is included with there (its groups' and its own, `all`; one included in several places under different conditions under `any` of them, unconditional once any place is), between the front and the back matter. `sourceModuleIds(source)` names the modules whose types are needed; module references inside a module are not followed (they are resolved inside it). It gives the manifest with its entries filled and everything else its own, so it prints back to its file, and `attributes`, the text attributes to resolve it with (the source's, its own over them): resolve `{ ...manifest, attributes }`. Issues (codes in `IssueCode`): `unknown-source-manual` (an error: no source, or one that cannot be read, worded alike, as the API passes a source hidden from the reader as none; the front and back matter stay), `derived-audience-wider` (an error: the manual is for a wider audience than its source, a manual without one being for the most restricted level; nothing is gathered, nor the source's text attributes), `derived-source` (an error: the source is derived, or the manual itself), `no-gathered-types` (an error: no types to gather), `safety-module-excluded` (a warning, `at` the module: a module of a safety type the rule leaves out), `unknown-excluded-module` (a warning) and `empty-derived-manual` (a warning; `emptyDerivedManual(source)` makes it, for a reader who may see nothing gathered). `parseManifest` refuses a derived file with entries, one without a rule and a rule on an assembled manual; `StoredManifest` is `Manifest` holding a stored manifest to that (an assembled one to at least one entry), apart from `Manifest` so it can still be extended (a working copy's `DraftManifest` may have no entries). `validateManifest` checks a rule's types against the configuration (`unknown-module-type`, `at: rule.moduleTypes`) and leaves the gathered entries' conditions to the source's checks. `manifestNamesModule` and `renameManifestModule` read and rewrite a derived manual's rule (its lists), not its gathered entries. An import bundle holds assembled manuals only (`ImportedManifest`). `isDerived(manifest)`; all of `derive.ts` is in `/core`.

**Gathering safety notices** (#670). A rule's `notices` (`NoticeRule`; absent: whole modules, exactly as above) gathers the safety messages (`safety` blocks) of the source's modules in place of the modules: `groupBy` (`NOTICE_GROUPINGS`, `DEFAULT_NOTICE_GROUPING` `module`) and `levels` (the hazard levels gathered, each once, in the order their groups come; none: every level, most severe first, `SAFETY_SEVERITIES`; `noticeLevels(rule)`). `DEFAULT_NOTICE_RULE` is one with nothing set; `noticeRuleOf(manifest)` a manifest's, if any. Every type is searched unless the rule names `moduleTypes` (then only those; `no-gathered-types` does not apply). `deriveManifest` then needs `module` (each module's source-language file; `readGatheringModules(ids, read, { followReferences, atOnce })` reads the source's modules, the front and back matter and, followed, the modules they refer to) and gathers, as above (order, once, conditions), each source module that holds a notice of a gathered level itself or through its module references (`noticeLevelsIn`, `referencedModuleIds`; variant blocks whatever their condition). Its issues: `safety-notice-excluded` (a warning, `at` the module holding the notices, its message naming no other module: notices of a gathered level reached only through modules the rule excludes or does not search, or notices of a level it does not gather in a module it searches) in place of `safety-module-excluded`, and `empty-derived-manual` worded for notices (`emptyDerivedManual(source, true)`). `resolveManual` resolves such a manual's front and back matter whole and gives each gathered module's notices only: the outermost `safety` blocks of the gathered levels wherever they sit (sections, lists, steps, tables, notes), through the variant blocks the variant shows (a hidden one holding a notice is listed in `hidden`) and the module references (to modules the reader may see, as `visible` says; cycles reported), each notice once (a snippet reached twice shows at its first place), resolved as anywhere: its ID `module--block` of the module holding it, as in the source manual, so it stays from release to release and in every language (each module in the manual's language, else the source language). Grouped by `module`: a module entry per gathered module (its title, its notices; none when it has none in this variant). Grouped by `level`: the front matter, then a group per level that has notices, in the levels' order, titled with the level's output label in the manual's language (`DANGER`, `GEFAHR`, or the configuration's `outputLabels`), holding per gathered module (in the source's order) a module entry with its notices of that level, then the back matter; a module with notices of two levels is an entry in both groups. A link from a gathered notice to a block of a searched module that is not gathered is `xref-outside-manual` (a warning), not `xref-unknown-block`.

**Update guides** (#906, `update-guide.ts`, in `/core` too). A manifest with `kind: update-guide` (printed right after `schemaVersion`) holds its steps in `guide` (`UpdateGuide`, printed last, in place of `entries`): `attribute`, the configured version attribute it follows; `versions`, the versions a reader picks from and to (dotted, quoted in YAML so `"2.10"` stays `2.10`, oldest first, each once, at least two, at most `MAX_UPDATE_VERSIONS`); `steps` (`UpdateStep`, at most `MAX_UPDATE_STEPS`), each a `module` (its title and body), the `version` that needs it, its `phase` (`UPDATE_PHASES`: `before`, `during` or `after` the update), optionally a `level` and a `when:` condition. A step applies to a jump from `from` to `to` when `from < version <= to` (`compareVersions`: `2.10` is after `2.9`, `2.3` is `2.3.0`). **The level is an audience level** (`audiences`, least restricted first; a step for `service` is for a reader who picks `service` or a more restricted level), not a list of its own: the levels are configured, labelled and translated already, ordered as a reader's level is, and are what the API's audience rules enforce, so a step never needs a second ordered list kept in line with the first. The step's module keeps its own `audience`, which decides who may read it at all. **Options** are the existing conditions on enum variant attributes (`when: cluster in (yes)`). Nothing is hardcoded but the three phases. `parseManifest` refuses an update guide with `entries`, one without a guide and a guide on another kind, and fills `entries` from the steps (`updateGuideEntries`: one module entry per step, in the PDF's order, without conditions), so whatever reads a manual's entries (the module index, translation status, releases, the checks for missing modules) reads an update guide's modules; `printManifest` never prints them. `manifestNamesModule` and `renameManifestModule` read and rewrite the steps.

- **Resolving a jump:** `resolveUpdateGuide(guide, { from, to, level?, options? }, levels)` (`guide` is `{ versions, steps }`: the manifest's `guide`, or the API's guide and step resources, whose steps carry the same `version`, `phase`, `level` and `when`; `levels` the configured audience IDs in order) gives `{ status: 'resolved', phases, count }`: all three phases in order, each with its steps (`{ step, index, version }`, `index` its place in manifest order) ordered by version, then by manifest order; only steps whose level is the reader's or a less restricted one (no level picked: every level) and whose condition holds for `options` (an option not set is false). `from >= to` resolves to no step with `reason: 'not-forward'`; a `from` or `to` that is no version of the guide (numerically) is `{ status: 'refused', reason: 'unknown-version', value }`, an unknown level `reason: 'unknown-level'`. Steps without a dotted version or with an unknown phase are left out. `orderedSteps` and `byVersionAndPhase` are the two orders.
- **Validation** (`validateManifest`, `at: guide.steps.<n>` from 0): `update-step-version` (an error: no version, or not a dotted version), `update-step-outside-versions` (a warning: a version no jump between the guide's first and last version crosses, i.e. at most the first or after the last, so the step is never shown), `update-step-phase` (an error: not one of `UPDATE_PHASES`), `unknown-audience` (a step's level), the step's condition as any (`unknown-variant-attribute`, …), and `unknown-variant-attribute` at `guide.attribute` for an attribute that is not a configured version attribute. Version and phase are checked here, not by the schema, so a draft with a step not filled in yet still saves.
- **The whole guide** (`resolveManual`, the PDF): every step whatever its condition, but one whose level is above the manual's audience or not configured (fails closed, as an audience does; `resolveUpdateGuide` never shows a step of an unconfigured level either), a group per version (`Version 2.0`, the output label `updateVersion` and the version), in it a group per phase that has steps (output labels `updateBefore`, `updateDuring`, `updateAfter`, in the manual's language), the steps in manifest order; a module in two steps is two copies (`--2`). `ResolvedManual.updateSteps` lists the steps the reader may see in that order, each with `index`, `version`, `phase`, `level`, `when` and its module entry (`entry`, the same object as in `entries`): what the API's step list is made of. A step's body is resolved for the variant resolved (the API's: the manifest's first), so content that differs per option belongs in steps of its own with a `when:`, not in `variant` blocks. An import bundle holds no update guides.

`resolveManual({ manifest, variant, lang, config, loadModule, loadTerm? })` produces one manual for one variant, language and audience:

- `variant` blocks and `when:` entries are applied; versions compare numerically (`2.10 > 2.9`, `2.3 = 2.3.0`)
- `module::` references are inlined (cycles are reported, not followed). **One block** (#223): a `moduleRef` with `block` places only that block of the module (looked up at any depth, `blockPlaces` in `block-places.ts`: every block by ID with the variant blocks around it, built once per module and resolution), resolved as in the whole module (its ID `module--block`, its variant blocks applied); inside a variant block the variant leaves out it places nothing (that variant block listed in `hidden`), and a block the module does not have is the error `module-ref-unknown-block` (`target` names the module and block). Each such inclusion counts the block against the expanded size as a whole module's inclusion counts the module (`Expansion.weighBlock`), and a reference to one block counts one like any. A cycle is one of modules: a reference to one block of a module on the way (the referring module itself included) is reported as `module-cycle`, whichever block it names. A derived manual gathering notices gives only that block's notices; `toChunks` writes only that block (without a variant, inside the quotes of the variant blocks around it); the DITA export puts the block in (a content reference names a whole module's topic). A link to a module placed only one block at a time lands on no other block of it: a warning `xref-outside-manual`, never `xref-unknown-block`. Each module is looked up once per resolution (#679: `loadModule` once per module and language, `visible` and the audience once per module), since one resolution has one variant, language and reader; nothing is kept from one call to the next, so two readers never share an expansion. A module referred to over several paths appears once per path, its copies' IDs `module--block--2`, `--3`, …. A manual gathering notices searches each module once, however many paths lead to it
- **The expanded size** (#679): past `MAX_EXPANDED_NODES` (500,000 content nodes: every object of an included module's blocks, counted once per inclusion, and each module reference met) or `MAX_EXPANDED_CHARS` (12,000,000 characters: the strings of each included module per inclusion, the values text attributes fill in and the messages of the reference cycles met) or `MAX_EXPANDED_TABLE_CELLS` (1,000,000 table cells, #686: each included table's rows times its columns, per inclusion, since few cells may span a table's whole 50,000-cell area), or with blocks and references nested deeper than `MAX_NESTING_DEPTH` (100 levels, a reference counting one), resolving stops and gives an empty manual with one issue, `expansion-too-large` (an error, the only one; its message says which limit), so references that multiply (a diamond, many levels deep) or chain thousands deep fail fast instead of holding the process or overflowing the stack. Over six times the largest manual measured (the scale generator's `xl` big manual, 1,600 modules: about 78,000 nodes, 1,900,000 characters, nested 3 deep); not a setting, so whether content resolves never depends on the deployment. Only what the reader may see counts: a reference to a module they may not see counts one
- **The chunk set** (#684, `ExpansionBudget`): what several walks may expand to together, counted with the same counters as each walk's own (`Expansion`). `toChunks({ …, budget })` spends every node, character and table cell it counts from it too, and throws `ExpansionBudgetError` (not an `ExpansionTooLargeError`: no one module is too large) once it is spent, checked before the limits of one walk; a walk that stops at those limits has spent what it walked. `ExpansionBudget.forContent(weights)` makes a set's budget from the weights (`weightOf`) of the modules it is made from: `MAX_CHUNK_SET_FACTOR` (4) times their sum, plus `CHUNK_SET_MODULES_AT_LIMITS` (32) times the limits of one walk, so a few modules at or past those limits fit, many do not; its `keptChars`, what the walks whose chunks the caller keeps may spend in characters, is four times the content's plus `CHUNK_SET_KEPT_AT_LIMITS` (8) times `MAX_EXPANDED_CHARS` (the caller holds it, as only it knows which walks it keeps). The scale generator's `xl` profile (77,000 module files, 88,000,000 characters of content) expands to 1.4 times its characters and 1.02 times its nodes and table cells, its most expanded module to under 2 times its own. Not a setting. The API holds a commit's chunks to it (`GET /chunks`, `chunk-set-too-large`).
- **The limits as one value** (#726, `ExpansionLimits`: `nodes`, `chars`, `cells`, `depth`): `EXPANSION_LIMITS` holds the four limits above (frozen), and is what everything holds content to. `Expansion`, `ExpansionBudget.forContent(weights, limits?)`, `toChunks({ …, limits? })` and `ExpansionTooLargeError(depth, limits?)` (its message names the limits it was held to) take another only so tests can cross the same boundaries with content a hundred times smaller; given none, each uses `EXPANSION_LIMITS`. A test seam, not a setting: nothing reads it from the environment or the content, and `resolveManual` takes none. The real limits are still tested at exactly the limit and one node more (`chunk-walk.spec.ts`).
- `{attribute}` references are replaced with the variant's value; one without a value (a module resolved on its own, with no manifest to give one) stays an `attribute` node, reported as `missing-text-attribute`, for the renderer to show
- modules above the manifest's audience are left out
- modules the reader may not see (`visible`, e.g. their roles' scope) are left out first, reported only as `outside-scope`
- a missing translation falls back to the source language; the manual's title and its groups' titles are in the manual's language, else the source language's (#731)
- block IDs become `module--block`, unique across the manual; `origins` and `anchors` map them back (a link to a whole module lands on its first block that is not a page break)
- `xrefTitles` (#796): the title of each module a cross-reference links to that is no entry of the manual (one outside it, or one it holds only through a module reference), in the manual's language or its fallback; what a cross-reference without its own text reads as in the HTML and the PDF instead of the module's ID. Only modules the reader may see (`visible`) and the manual's audience allows; the lookup reports nothing
- callouts (#498): each image keeps the callouts the variant shows, in number order, without their conditions and with `calloutOrder: 'manual'` (so `numberCallouts` reads the same numbers); `callouts` maps each image's output ID to its callouts' numbers. A callout reference names its image by output ID (the copy in the same inclusion of the module, so a module included twice links each reference to its own copy) and `calloutNumber(manual, ref)` gives its number. One whose callout or image the variant leaves out, or that names nothing, keeps its callout ID but names no image (`block: '_'`, `UNRESOLVED_CALLOUT_IMAGE`, a block ID no output ID is), so it has no number. A hidden one is a `hidden-callout` warning; one to a callout the module does not have is an `unknown-callout` error
- the terms its content links (`terms`, #245): each linked term `loadTerm` gives, once, with its preferred variant and definition in the manual's language, else in the source language (`lang` says which, for the renderer to mark it), sorted by the preferred variant with `Intl.Collator` in the manual's language; a term `loadTerm` does not give is left out (its links stay plain text). `glossary` is the manifest's `glossary: true`: the outputs end the manual with a glossary of those terms

Problems come back as `issues` (missing modules, translations or attribute values, unset variant attributes, cross-references outside the manual) instead of exceptions, so a preview can still render. An issue found at a block names it in `at` (`{ module, block }`, unqualified IDs: for a module reference, the referring module's block); a cross-reference's issue names what it links to in `target`.

What the variant's conditions left out comes back as `hidden` (`HiddenContent`), for a preview to list: variant blocks (`kind: 'block'`, the module, the block's ID, its condition and its unresolved content), module entries (`module`, with its title) and groups (`group`). Only the outermost hidden content, each once, in document order, and only what the reader could otherwise read: a module entry outside `visible` or above the audience is not listed.

## Page designs

How a manual's pages look (#390): one `PageDesign` (Zod, `page-design.ts`) per file, `design/<id>.yaml` in the content repository, written and reviewed like the configuration. The ID is the file name's, a slug like a module's; `builtin` is reserved for the built-in design (`DEFAULT_PAGE_DESIGN`), which a manual gets when neither its manifest (`design`) nor the configuration (`pdf.design`) names one. Every setting but `name`, `preset` and `colours` has a default, so a file holds only what it changes (`src/fixtures/page-design.yaml` holds all of them).

- **Settings.** `preset` (`PAGE_DESIGN_PRESETS`: `classic`, `image-led`, `minimal`) decides the title page's layout and its regions (`regionSlots(preset)`; `back` and `back-footer` on the back page with every preset); `page` (`PAGE_SIZES`: `a4`, `us-letter` or `a5`, portrait, #668; `PAGE_SIZE_MM` their width and height; margins in mm, `doubleSided`); `colours` (`primary`, `accent`, `text`, `#rrggbb`); `fonts` (`body`, `heading`: a family and its faces as `sha256:<hash>` files, and `embeddingAllowed`, the confirmation that the licence allows embedding); `logo` (`light`, `dark`); `titlePage.fields` (`TITLE_PAGE_FIELDS`); `regions` (per slot, AsciiDoc blocks: headings one level deep, a section at the region's top whose title prints as an unnumbered heading outside the contents and bookmarks; no nested sections, page breaks, module references or cross-references); `coverImage` (a default, and per variant the first rule whose `when` holds); `backPage` (`position`, `BACK_PAGE_POSITIONS`: `last`, the default, or `inside-cover`, on the back of the title page; copyright, document number, date; no back page without it; the manufacturer it prints is the configuration's `manufacturer`, #395); the running `header` and `footer` (`left`, `centre`, `right`, inline content, for `default` pages, the `first` page and, printed double-sided, `even` pages); `headings` (numbering per level, sizes from `TYPE_SCALE`, colour role, a page break before level 1); `body` (font size in pt, line height, paragraph spacing in pt, 1 or 2 columns); `tables` (header tint, borders `none`, `horizontal` or `grid`, zebra rows); `steps` (`filled-circle` or `number`); `notes` (`tinted` or `framed`); `safety` (`ansi-z535` or `iso-3864`, ISO 3864 with EN 82079-1: the layout of safety messages; their colours, signal words and symbols are the standard's, `SAFETY_FIXED_SETTINGS`, never the design's).
- **Translatable text.** A region's blocks, a header or footer place, the cover image's alt text and the copyright are each one value for every language or a mapping by language tag (`Translatable`); a language without its own takes the source language's.
- **Translation record** (#568). `translations` (optional, printed after `regions`, languages and keys sorted) is the region text's record per target language: `{ sourceCommit, blocks }`, `blocks` keyed `<slot>.<blockId>` (`DesignUnitKey`) with the source hash each translation was made from, as a module's `TranslationRecord` is, kept in the design file itself. `designUnits(design, source)` lists the region text's translatable units (`DesignUnit`: a `TranslatableUnit` keyed `<slot>.<blockId>`, with its `slot` and `block`), each region's source-language text (`regionSourceText`), slots in the preset's order; only region text has units (header and footer places, the cover's alt text and the copyright have none yet). `designSourceHashes(design, source)` gives their hashes, `compareDesignWithRecord(design, lang, source)` each unit's state in `lang` (`missing` where the region has no text of its own in `lang`, else `up-to-date` or `outdated` against the record), `hasDesignTranslation` whether any region has. Editing the source text leaves the record as it is, so the translation shows as outdated.
- **Placeholders** (`placeholder.ts`, schema-free): `PLACEHOLDER_KEYS` (`title`, `subtitle`, `product`, `variant`, `product-version`, `language`, `release`, `date`, `document-number`, `revision-number`, `audience`, `manufacturer-name`, `manufacturer-address`, `manufacturer-contact`, `manufacturer-website`, `chapter`, `page`, `page-count`; `MANUFACTURER_PLACEHOLDER_KEYS` the four from the configuration's `manufacturer`). `pageDesignShowsRelease(design)` says whether a design prints the release or its date anywhere (a title page field, the back page's date, a placeholder in a region or a running header or footer), so a release's PDF of it is never reused from an earlier release. The page keys (`PAGE_PLACEHOLDER_KEYS`: `chapter`, `page`, `page-count`) are the renderer's to fill per page; `subtitle`, `product`, `product-version`, `document-number` and `revision-number` take the manifest's text attribute of the same name. Outside a renderer a placeholder reads as `[key]` (`placeholderText`): in plain text, Markdown, the HTML preview and XLIFF (`<ph>` with its key).
- **File.** `parsePageDesign(text, { id })` (`PageDesignParseError`; at most `MAX_PAGE_DESIGN_FILE_LENGTH` characters, no YAML aliases) and `printPageDesign` (canonical: every setting in the schema's order, defaults included, languages sorted, regions in the preset's order; `printPageDesign(parsePageDesign(t)) === t` for every `t` it prints). Region text is AsciiDoc blocks, header and footer text AsciiDoc inline markup, a cover rule's `when` a condition as modules write it.
- **Validation.** `validatePageDesign(design, config)` gives `PageDesignIssue`s (`severity`, `code`, `message`, `at` a dotted path, `block` a region's block): `unknown-preset`, `unknown-region`, `unknown-placeholder`, `unknown-language`, a region's block issues as a module's (`validateModule`'s codes), a cover rule's condition issues, `low-contrast` (a warning: a colour under `MIN_TEXT_CONTRAST`, 4.5:1, against white, `contrastRatio`), `missing-cover-image` (a warning for `image-led` without one), `fonts-not-confirmed` (an error: fonts without `embeddingAllowed`), `missing-manufacturer` (a warning at `backPage`: a back page while the configuration has no `manufacturer`) and `region-languages-differ` (a warning: a region whose text in one language has other block or item IDs than the source language's, else the first language's; `regionBlocksDiffer` and `regionDifferenceMessage` tell how). `pageDesignAssets(design)` lists the files it names; `pageDesignAssetIssues(design, stat)` checks them against a store (`missing-asset`; `invalid-font` for a font that is no TrueType, OpenType, WOFF or WOFF2 file by its first bytes, `fontFormatOf`; #555).
- **Resolution** (`page-design-resolve.ts`). `pageDesignIdFor(manifest, config)` is the manifest's `design`, else `pdf.design`, else `builtin`; `choosePageDesign({ manifest, config, loadDesign })` loads it, and a design that is not there is the issue `unknown-page-design` with the built-in design used, so a preview still renders. `resolvePageDesign({ design, manifest, variant, lang, config, release?, date? })` gives what the renderer needs for one manual, variant and language (`ResolvedPageDesign`): every text in the manual's language, its placeholders filled (the title, the language's own name, the variant's label (the title, the variant's and the audience's labels in the manual's language, else the source language's, #731), the release and the date in the language's format with `Intl` (given only for a release's PDF, #395; a preview leaves them as placeholders), the configuration's `manufacturer` (`manufacturerValues`: the address lines joined with ", "), the audience's label, the manifest's text attributes) but the page keys, `{attribute}` references filled, variant blocks in regions applied, the cover image (the manifest's for the variant, else the manifest's default, else the design's first matching rule, `manualCoverImage`; a manifest's alternative text is reported at `manual.coverImage.…alt`), the `even` header and footer only when double-sided, fonts only when embedding is allowed. Problems come back as issues (`name` the placeholder, field, attribute or language they are about): `missing-translation`, `dropped-text` (a text in neither the manual's language nor the source language, left out), `region-languages-differ` (the manual's language's region text has other block IDs than the source's), `missing-placeholder-value`, `missing-text-attribute`, `missing-variant-attribute`.
- **Own template** (#396). `template` (optional, a slug, printed after `preset`) names an organisation's own Typst template, the folder `templates/<id>/` of the content repository with its entry file `manual.typ` (`DESIGN_TEMPLATES_DIR`, `DESIGN_TEMPLATE_ENTRY`, `designTemplateDir(id)`, `designTemplatePath(id)`), which lays the PDF out in place of the preset's template; the preset still decides the title page's regions. A folder holds at most `MAX_TEMPLATE_FILES` (200) files and `MAX_TEMPLATE_BYTES` (16 MiB). `pageDesignTemplateIssues(design, templateIds)` is the error `unknown-template` (at `template`) when the repository has no such template; the PDF then uses the preset's. The contract and the example template: `@openfolia/render-typst`'s README, "Own templates".
- `@openfolia/content-model/core` holds the schema-free part: the option lists, `contrastRatio`, `fontFormatOf`, `textInLanguage` and the placeholder helpers (`page-design-options.ts`, `placeholder.ts`).

## Translation

A translation is a module file in a target language with the source module's block IDs (`modules/<lang>/<id>.adoc`). What it was translated from is recorded block by block, so the system knows which blocks changed in the source since.

- **Units.** `translatableUnits(module)` lists the module's translatable units in document order, each with its `blockId`, its `kind` (the block type, or `item` for a list item or procedure step) and its `parts` (`{ field, content }`, inline content): a paragraph's content; the title of a section, procedure or table; a list item's or step's own text; an image's `alt` and `title`; an attachment's `name` and `description`; a safety block's `hazard`; an FAQ entry's `question`; an image callout's `legend` (#548), a unit of its own with `kind: 'callout'`, the callout's ID as its `blockId` and its image's as `image`, right after the image's unit, for every callout whichever variant shows it. Plain text fields (alt text, attachment name and description) are one text run. The blocks inside sections, notices, safety, FAQ answers, variant blocks, list items and table cells are units of their own. `literal` and `passthrough` are not translated; a module reference, a page break and a block with no text of its own (a list, an admonition, a variant block, a procedure or table without a title) have none. The module's title and keywords are metadata, not blocks, and have no unit.
- **Source hash.** `sourceHash(unit)` is the SHA-256 (64 lowercase hex characters, `SourceHash`) of the unit's parts as canonical JSON: the fields and their inline content with marks, attribute references, cross-references and keys. Units are read from the normalized module, so formatting the canonical printer removes (mark order, how text runs are split) does not change it; a property test checks every hash survives `printModule` and `parseModule`. Text is compared in NFC, so the same text typed decomposed hashes alike. The block's ID and type and its nested blocks take no part; `sourceHashes(module)` gives every unit's hash by block ID, worked out once per module object. A change to what is hashed bumps the record's `schemaVersion`. `sha256Hex(text)` is the hash used: synchronous and without Node's `crypto`, so the editor hashes alike.
- **Translation record** (`TranslationRecord`, Zod): `schemaVersion` (1), `sourceCommit` (the full commit ID of the source that was translated) and `blocks` (block ID → the source hash its translation was made from). Stored as YAML next to the translated file (`modules/<lang>/<id>.translation.yaml`, `@openfolia/content-repo`); `parseTranslationRecord` reads it (`TranslationRecordParseError`), `printTranslationRecord` writes it canonically (blocks sorted by ID). `translationRecordOf(source, commit)` is the record of a translation made from `source` at `commit`. A block ID `__proto__` is never recorded (refused in a file), so such a block always counts as outdated.
- **Plain text.** `plainTextOf(content)` gives inline content as one string for a reader that takes plain text (the style review's model): text runs as they are, a hard break as `\n`, an attribute reference as `{name}`, a cross-reference as its link text (`[xref]` without one), a keyboard shortcut as its keys joined by `+`; every stretch that is not a text run is an atom (`atoms`, offsets in UTF-16 code units). `isTextRange(plain, start, end)` says whether a range is non-empty, in bounds, whole surrogate pairs and clear of atoms, so a suggested change never cuts into an inline node.
- **State.** `compareWithRecord(source, record)` gives each unit of the source module `up-to-date` (the record names it with the hash it has now) or `outdated` (changed since, or never translated). Without a record (a translation made before tracking) every block is outdated. Blocks the record names that the source no longer has are not listed.

## Retrieval chunks

`toChunk({ module, config, loadModule, variant?, budget? })` (`lib/chunk.ts`) turns one module in its language into a retrieval chunk: its text as Markdown (`lib/markdown.ts`: CommonMark with GFM tables; headings, lists, numbered procedure steps, Markdown tables, safety blocks and notes as quotes headed by the language's signal word or caption, images as their alt text, attachments by name; every markup character in the content backslash-escaped), the module's metadata, `conditions` (its variant blocks' conditions as `when` text), `sourceHash` (`moduleSourceHash`: SHA-256 of the translation units' source hashes, or of the canonical AsciiDoc for a module without any), `contentHash` (SHA-256 of the text) and `sources` (the module files the text was made from). Module references are inlined as `resolveManual` does (source-language fallback, no cycles), only those `loadModule` gives (the caller scopes it) and none more restricted than the module itself. With `variant`, variant blocks are resolved for it; without, each is kept as a quote headed by `**when**` and its condition. The text comes from the parsed module, so formatting of the file and block IDs change neither it nor `contentHash`. `toChunks(input)` gives that chunk first, then one per FAQ entry in the module (at any depth, not those a module reference brings in, which are their own module's): `entry` holds the entry's block ID, its question as plain text and the conditions of the variant blocks around it (`within`); its text is the question as `#` heading and the answer, its `sourceHash` is of the entry's own units, its `conditions` are those around it and in it, and with `variant`, an entry whose surrounding conditions do not hold has no chunk. The module's chunk keeps its entries (the question as a bold line, then the answer). Each module a reference names is read once per call, however many paths lead to it, and the walk is held to the limits of resolving ("The expanded size", `lib/expansion.ts`, #681): one count per `toChunks` call (its module's chunk and its entries' together), which also counts the titles cross-references show and the Markdown written around nested blocks (each quote, list and table, once per level) and each table's grid (a cell per row and column, counted before it is made). Past a limit it throws `ExpansionTooLargeError` (`depth`: the nesting limit; `reason`: `size` or `depth`), and gives no chunk; the API leaves such a module out of a commit's chunks and cuts the others as usual (#688). Only what `loadModule` gives counts, and nothing is kept from one call to the next, so a reader who may not see part of the content gets the chunks of what they may see. The API serves chunks at `GET /chunks` (`backend/api/README.md`, "Chunks").

## Import format

Content from another system arrives as an **import bundle**: a ZIP with `import.json` (a `formatVersion`, an optional `source`, `modules` as `Module` JSON in any language with `meta.source` for traceability, `manuals` as manifests and the converter's `report` of what it could not map) and `assets/<sha256>`, the files images and attachments refer to as `sha256:<hash>`. Converters live outside this repository; [`docs/import-format.md`](docs/import-format.md) describes every field and how to write one, and `src/fixtures/import-example/` is an example bundle.

- `ImportDocument` (Zod) is the schema of `import.json`; its JSON Schema is published as `import-format.schema.json` (`@openfolia/content-model/import-format.schema.json`), generated by `nx run content-model:import-schema` and held to the Zod schema by a test.
- `validateImport(bundle, config, { existing })` (async: files are hashed with Web Crypto) takes the unpacked archive (`files`: path → bytes) and gives, per module, manual and file, issues with a stable `code` and a JSON Pointer: schema errors, `validateModule` and `validateManifest` against the target's configuration, references that resolve neither in the bundle nor in `existing`, missing files and hash mismatches, `passthrough` counts, and ID clashes with `existing` as `info` (the import decides). A newer `formatVersion` is refused (`unsupported-format-version`); older ones are migrated (`IMPORT_FORMAT_MIGRATIONS`, none yet). Reading the ZIP and its size limits are the caller's.
- `assetRefOf(bytes)` is the `sha256:<hash>` of a file.

## iiRDS mapping

`iirds` in `openfolia.yaml` (optional; `iirdsMappingSchema`, `IirdsMapping`, #431) maps the project's configuration to the iiRDS vocabulary for the API's iiRDS export, by the standard's names (the lists `IIRDS_TOPIC_TYPES`, `IIRDS_DOCUMENT_TYPES`, `IIRDS_INFORMATION_SUBJECTS`, `IIRDS_LIFECYCLE_PHASES`, `IIRDS_PRODUCT_CLASSES`, `IIRDS_QUALIFICATION_CLASSES`; a name it does not have is refused):

```yaml
iirds:
  baseIri: https://docs.example.com/iirds/ # absolute http(s), ending in "/": every IRI is made under it
  documentTypes: [OperatingInstructions] # each manual's, at least one
  manualDocumentTypes: { service: [MaintenanceInstructions] } # a manual's own, instead
  moduleTypes:
    task: GenericTask # a topic type
    safety: { topicType: GenericConcept, subjects: [SafetyInstruction] }
  audiences: { operator: Role, technician: SkillLevel }
  facets: { region: ProductVariant } # ProductVariant, Component, ProductFunction or ProductProperty
  variantAttributes: { model: ProductVariant }
  lifecyclePhases: { facet: phase, values: { use: Operation } } # a facet whose values are phases
```

Every map is optional. A value the configuration defines that the mapping leaves out, or a key naming nothing, is never refused: `iirdsMappingIssues(config)` lists them (`unmapped-*`, `unknown-mapping-key`; a `manualDocumentTypes` key naming no manual is not among them, since the configuration does not know the manuals) and an export leaves that metadata out with a warning. `moduleTypeMapping` reads a module type's topic type and subjects. `printConfig` writes the mapping canonically (empty maps left out).

## DITA mapping

`dita` in `openfolia.yaml` (optional; `ditaMappingSchema`, `DitaMapping`, #432) says how the DITA import
(`@openfolia/dita`, `docs/dita-import.md`) maps a DITA 1.3 project to this configuration. Keys are DITA
names (`DitaName`: one token), values the project's own IDs:

```yaml
dita:
  moduleTypes: { task: procedure } # topic type (root element) → module type
  outputclasses: { howto: procedure } # an @outputclass token → module type; wins over moduleTypes
  defaultModuleType: concept # any other topic; default: a type named like the topic type, else the first
  profiling:
    product: { variantAttribute: model, values: { gp2-basic: basic } } # values by the same IDs unless mapped
    audience: { audience: { user: operator } } # values → audience levels
  textKeys: { prodname: product-name } # an empty <ph keyref="prodname"/> → the text attribute
  hazardSymbols: { hot-surface.svg: w017 } # a <hazardsymbol>'s file name or key → safety symbol
  ditavalDefault: none # a DITAVAL file no map names: none (not applied, the default) or all (a variant of every manual)
```

Every map is optional, and without any, a profiling attribute named like a variant attribute maps
to it and `audience` maps to the audience levels of the same IDs. A value naming nothing configured
is never refused: `ditaMappingIssues(mapping, config)` lists it (`unknown-module-type`,
`unknown-variant-attribute`, `unknown-variant-value`, `unknown-audience`,
`unknown-text-attribute`, `unknown-safety-symbol`, with its `path` in `dita`), the import reports
it and uses its default there, and `GET /config` shows them (`meta.ditaIssues`). `printConfig`
writes the mapping canonically (empty maps and the default `ditavalDefault` left out). The names
of the standard are lists too (`DITA_TOPIC_TYPES`, `DITA_FILTER_ATTRIBUTES`).

## Entry points

- `@openfolia/content-model` (`src/index.ts`): everything, the schemas (zod) and the YAML files
  included. The API server, the renderers and the editor's model package use it.
- `@openfolia/content-model/core` (`src/core.ts`): every type of the full entry, and the helpers whose
  modules import neither zod nor yaml (`walk`, `plainTextOf`, `formatCondition`, `parseCondition`,
  `isCondition`, `evaluateCondition` and `compareVersions` (`condition-eval.ts`, #669), `normalizeModule`, `translatableUnits`, `variantSlug`, `resolveOutputLabels`, `textIn`, `labelsIn`, `labelOf` and `variantLabel` (#731),
  `formatFileSize`, `productFacet`, the snippet, structure and callout helpers, the writing checks
  (`checkWriting`, `compileWritingRules`, `StylePattern`), …). For a browser screen
  that reads and shows content: the full entry brings zod and yaml (about 540 kB raw) to every
  screen that imports it, through its schemas. Each value is the full entry's own (one module, one
  identity).
- `core.spec.ts` follows `core.ts`'s run-time imports (TypeScript's output, type-only imports
  erased) and fails if they reach any package. A helper that should be in `core` lives in a file
  without schemas (`variant-slug.ts`, `translatable-units.ts`, `facets.ts`, `mark-order.ts`, `localized-text.ts`, `config-units.ts`,
  `condition-check.ts`, `condition-eval.ts`, `callouts.ts`, `style-pattern.ts`, `writing-check.ts`),
  and the full entry exports it too.
- `isCondition` (`condition-check.ts`) answers what `Condition.safeParse(x).success` answers,
  without the schema; a property test holds the two to the same answers.
