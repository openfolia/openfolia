A public demo lets strangers try OpenFolia without signing up. Each visitor gets an instance of
their own, which nobody else reaches and which is deleted when they leave. OpenFolia provides
three parts of this: the **sandbox mode** of the API, the **sandbox image**, which runs one such
instance in one container, and the **launcher**, which starts a container per visitor and routes
their browser to it.

## The sandbox mode

`CCMS_PUBLIC_SANDBOX=on` (with demo sign-in, `CCMS_AUTH_MODE=demo`) makes an instance a sandbox:

- **Nothing leaves it.** No email, webhook, AI provider, audit sink or identity provider. The
  server refuses to start with a setting that would reach outside, and names it.
- **Nothing reaches other people.** Adding users, service accounts, tokens, invitations, uploads,
  imports, template changes, webhooks and backups are refused (403 `sandbox-not-allowed`).
- **What a visitor makes is capped:** the size of a module and a comment, the change sets, modules
  and manuals made, the releases an hour, the PDFs rendered at once and the bytes written over
  the session (422 `sandbox-limit-reached`). The `CCMS_SANDBOX_*` settings in `.env.example`
  set them.
- **The session ends** after `CCMS_SANDBOX_IDLE_MINUTES` without a request (default 30), at the
  latest `CCMS_SANDBOX_MAX_MINUTES` after the start (default 90). The editor shows a banner with
  the time left.
- **The banner can link the reader portal:** with `CCMS_SANDBOX_PORTAL_URL` (an https address,
  never called by the API) it shows "See the reader portal", opening it in a new tab. The launcher
  sets it on each sandbox from `CCMS_LAUNCHER_PORTAL_URL` when that is an https address.

`GET /sandbox` names the limits, what was used and `meta.endsAt`. A normal instance answers it
with 404.

## The sandbox image

`ghcr.io/<owner>/openfolia/sandbox` holds the API in sandbox mode, the editor, an embedded
database and the content repository, with the demo's finished state baked in: the sample manuals,
two releases with their PDFs, a change set in review with comments, and the three demo people
(an author, a reviewer, an admin). The state is there in English and in German. It is built for
`linux/amd64` and `linux/arm64`.

```sh
docker network create --internal sandboxes
docker run -d --name sandbox-<id> --network sandboxes --network-alias sandbox-<id> \
  --read-only --tmpfs /tmp:rw,size=256m,mode=1777 \
  --cap-drop ALL --security-opt no-new-privileges:true \
  --memory 1g --memory-swap 1g --cpus 1 --pids-limit 256 \
  --log-driver local --log-opt max-size=5m --log-opt max-file=2 \
  -e CCMS_SANDBOX_LANG=en -e CCMS_EDITOR_HOSTS=sandbox-<id>.demo.example.org \
  ghcr.io/<owner>/openfolia/sandbox:vX.Y.Z
```

- It is **ready in under 5 seconds**, and its health check passes then.
- It serves **one port, 8080**: the editor, which proxies `/api` to the API inside. The API and the
  database listen on the container's loopback only.
- It runs as an unprivileged user on a read-only file system, needs **no outbound network** and
  no volume. Everything a visitor makes lives in the tmpfs, so removing the container removes it.

| Setting             | What it does                                                              |
| ------------------- | ------------------------------------------------------------------------- |
| `CCMS_SANDBOX_LANG` | `en` or `de` (default `en`): the baked state in English or in German.     |
| `CCMS_EDITOR_HOSTS` | The host name the visitor's browser uses (default `localhost,127.0.0.1`). |
| `CCMS_SANDBOX_*`    | The limits and the session length, as for any sandbox.                    |

The image makes its own API token, database and secret key. It refuses to start with
`CCMS_API_TOKEN`, `CCMS_DATABASE_URL`, `CCMS_SECRET_KEY`, `CCMS_WEBHOOKS_SECRET_KEY`,
`CCMS_EDITOR_API_TOKEN` or `CCMS_EDITOR_API_URL` set.

## The launcher

The launcher is the demo's front door (`ghcr.io/<owner>/openfolia/sandbox-launcher`). Its start
page, in English and German, says what the demo is and starts a sandbox at a button. Then the
visitor's browser is in the editor of their own sandbox, at the demo's own address.

- **Proof of work instead of a captcha.** Before a start the browser solves a small puzzle (about
  a second on a phone), so starting sandboxes in bulk costs real work.
- **One cookie binds a browser to its sandbox.** It is random, `HttpOnly`, `Secure` and
  `SameSite=Strict`. The same address in another browser shows the start page, never the sandbox.
- **Limits:** at most `CCMS_LAUNCHER_MAX_SANDBOXES` at once (default 5, for 8 GB), one at a time
  and three a day per address, a sandbox ends after 30 minutes without activity and after 90 at
  the latest, and every address and sandbox has a request rate. When all are taken, the start
  page shows the demo's films and tries again by itself.
- **Clean-up:** a sandbox is removed when its time is up, every sandbox when the launcher stops,
  and any it does not know when it starts.
- **Kept apart:** each sandbox has an internal network of its own, which only the launcher joins.
  Only the launcher's **agent** talks to the container runtime, over a private network and with a
  token; the launcher itself never has the runtime's socket.
- **A shared portal**, built once from a normal instance with the demo's released manuals
  (`ghcr.io/<owner>/openfolia/demo-portal`), never from a sandbox: a sandbox's demo sign-in is an
  admin.

`deploy/compose.demo.yaml` runs the launcher, its agent, the portal and a TLS proxy on one host.
The settings (`CCMS_LAUNCHER_*`) are in `.env.example`; the steps are in `deploy/README.md`, "The
public demo".

### What the demo stores

The launcher's page `/_demo/data` says this to visitors, in English and German, so your privacy
policy can link to it:

- **One cookie, strictly necessary:** a random key that ties the browser to its sandbox. It needs
  no consent and expires with the sandbox.
- **The IP address only as a keyed hash** (HMAC-SHA-256 with a secret of the deployment,
  `CCMS_LAUNCHER_ADDRESS_SECRET`), for the per-address limits, in memory for 24 hours at most.
  The address itself is never stored, logged or passed to the sandbox.
- **The sandbox until it ends**, then nothing: what a visitor writes is deleted with it.
- **Logs without addresses or content:** when sandboxes start, end or are refused, and why.

The header's logo and the footer link your homepage, imprint and privacy policy when you set
`CCMS_LAUNCHER_HOMEPAGE_URL`, `CCMS_LAUNCHER_IMPRINT_URL` and `CCMS_LAUNCHER_PRIVACY_URL`.

## How many fit on a host

Measured on an arm64 machine with one CPU per sandbox:

| Phase                                    | Memory         |
| ---------------------------------------- | -------------- |
| Started, idle                            | 430 to 457 MiB |
| Editing (a change reviewed and merged)   | 445 MiB        |
| Rendering a release (24 PDFs, about 7 s) | 670 to 735 MiB |

Memory stays at its peak after a release. Idle, a sandbox uses about 1 % of a core; a release keeps
one core busy for about 7 seconds. Keep about 2 GB for the host, then plan **one sandbox per GB**
of the rest: 14 on a 16 GB host, 60 on a 64 GB host. With fewer cores than that, renders wait for
each other when many visitors cut releases at once. The full numbers and how to measure them on
your own host (`deploy/sandbox-test.sh`) are in `deploy/README.md`, "The sandbox image".
