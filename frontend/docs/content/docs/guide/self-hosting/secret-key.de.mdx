Der Instanzschlüssel versiegelt (AES-256-GCM) jedes Geheimnis, das der Server speichert und
selbst benutzen muss: die Signatur- und Header-Geheimnisse der Webhooks, wartende E-Mails, das
S3-Geheimnis und den aufbewahrten Backup-Schlüssel der Backups. Er liegt nie in der Datenbank;
ein Dump der Datenbank allein öffnet also keines davon. Er wird nie protokolliert, nie von der API
ausgegeben und nie ins Audit-Log geschrieben.

## Woher er kommt

Die API sieht in dieser Reihenfolge nach:

1. `CCMS_SECRET_KEY`: der Schlüssel selbst, 32 Zufallsbytes als Base64 (`openssl rand -base64 32`)
   oder 64 Hex-Ziffern. Dann wird keine Schlüsseldatei gelesen oder geschrieben.
2. Die Schlüsseldatei, `CCMS_SECRET_KEY_FILE`. Standard ist `ccms-secret.key` im Ordner, der das
   Inhalts-Repository enthält: `/data/ccms-secret.key` in den Containern.
3. Sofern nicht `CCMS_SECRET_KEY_GENERATE=false`: ein neuer Schlüssel, beim ersten Start erzeugt
   und als Schlüsseldatei geschrieben, mit den Rechten 0600 (ihr Ordner 0700).

Ohne Schlüssel bleiben Webhooks und E-Mail aus. **Verwaltung › System** zeigt, woher der
Schlüssel kommt, nie den Schlüssel selbst.

Für einen einzelnen Server setzen Sie nichts: Der erste Start legt die Schlüsseldatei auf dem
Volume `data` an.

## Das Backup des Schlüssels

Sichern Sie den Schlüssel zusammen mit der Datenbank: Eines ohne das andere verliert jedes
gespeicherte Geheimnis. Der [Backup-Dienst](/de/guide/self-hosting/backups) legt die
Schlüsseldatei in jedes Backup. Wenn Sie `CCMS_SECRET_KEY` setzen, bewahren Sie ihn in Ihrem
Geheimnisspeicher auf.

Die API verweigert den Start, mit einer Meldung und nie mit einem neuen Schlüssel, wenn der
Schlüssel nicht öffnet, was die Datenbank enthält (ein anderer Schlüssel gesetzt, die falsche Datei
eingehängt), oder wenn die Datenbank versiegelte Geheimnisse enthält und kein Schlüssel da ist. Es
genügt dann, die richtige Schlüsseldatei wiederherzustellen.

## Mehrere Server

Geben Sie allen Servern denselben Schlüssel: Setzen Sie `CCMS_SECRET_KEY` überall auf denselben
Wert, oder lassen Sie sie eine Schlüsseldatei auf einem Volume teilen. Setzen Sie
`CCMS_SECRET_KEY_GENERATE=false`, wo ein fehlender Schlüssel nie neu erzeugt werden darf, etwa in
einer gehosteten Umgebung mit Geheimnisspeicher.

## Den Schlüssel rotieren

Die Rotation versiegelt jedes gespeicherte Geheimnis in einer Transaktion neu, mit einem neuen
Schlüssel. Die Geheimnisse selbst ändern sich nicht: Empfänger von Webhooks merken nichts.

1. Halten Sie alles an, was den Schlüssel hält, auch die Worker:
   `docker compose stop api worker backup`.
2. Nur wenn `CCMS_SECRET_KEY` den Schlüssel setzt: Setzen Sie `CCMS_SECRET_KEY_NEW` auf den neuen
   Schlüssel (gleiches Format), in derselben Einstellungsdatei, etwa `deploy/api.env` (nur für Sie
   lesbar: `chmod 600 deploy/api.env`). Mit der Schlüsseldatei erzeugt die Rotation den neuen
   Schlüssel selbst.
3. Starten Sie die Rotation:

   ```sh
   docker compose run --rm api node dist/secrets/rotate-secret-key.main.js
   ```

   Sie wendet ausstehende Migrationen an, prüft den aktuellen Schlüssel wie ein Start und meldet,
   wie viele Geheimnisse sie neu versiegelt hat. Einen Schlüssel gibt sie nie aus.

4. Mit der Schlüsseldatei: Die Datei enthält jetzt den neuen Schlüssel. **Sichern Sie sie erneut.**
   Mit `CCMS_SECRET_KEY`: Setzen Sie ihn auf jedem Server auf den neuen Schlüssel und entfernen
   Sie `CCMS_SECRET_KEY_NEW` (lassen Sie es nie gesetzt).
5. Starten Sie den Stack: `docker compose up -d --wait`.

Ein Geheimnis, das schon der alte Schlüssel nicht öffnete, bleibt, wie es war, und wird gezählt:
Geben Sie diesem Webhook ein neues Geheimnis. Eine abgebrochene Rotation lässt den alten Schlüssel
gültig; der nächste Start legt den unfertigen neuen Schlüssel als
`<Datei>.next.discarded.<Zeit>.<ID>` beiseite. Entfernen Sie diese Dateien, sobald kein Backup sie
mehr braucht. Eine Schlüsseldatei, die ein symbolischer Link ist (ein eingehängtes Geheimnis),
wird durch eine gewöhnliche Datei ersetzt: Rotieren Sie einen solchen Schlüssel deshalb mit
`CCMS_SECRET_KEY_NEW` und passen Sie die Einhängung an.

## Der alte Name

`CCMS_WEBHOOKS_SECRET_KEY` ist der alte Name von `CCMS_SECRET_KEY`. Er wird noch gelesen, wenn
`CCMS_SECRET_KEY` nicht gesetzt ist, mit einer Warnung beim Start. Benennen Sie ihn um.
